# AI Customer Support API

A portfolio project: a FastAPI service that answers customer support questions using Claude. It looks up the signed-in customer's own data and searches help articles with tools, returns validated structured output, and keeps persistent multi-turn conversations.

The data belongs to **Flowdesk**, a fictional project management product. All customers and billing records are fake, generated by a seed script.

## What it does

- **Answers from real records:** Claude calls read-only tools to look up the customer's profile, subscriptions, invoices, payments and support tickets.
- **Answers from help articles:** for how-to and policy questions, Claude searches Flowdesk's help articles, stored in Qdrant, with a query it writes itself.
- **Returns structured output:** each answer is validated against a Pydantic model and includes a customer-facing reply, the help-article chunks it cites, plus a category, priority, summary and human-review flag.
- **Keeps conversations:** follow-up questions have the context of earlier turns, including tool calls and results, stored in SQLite.
- **Isolates customers:** Claude can't choose whose data it sees, because the account tools take no input, the help-article search takes only a query, and the customer ID comes from the authenticated request.

## Tech stack

Python 3.13, FastAPI, Pydantic, SQLModel, SQLite, the Anthropic Python SDK with Claude Haiku 5.5, sentence-transformers, Qdrant, Langfuse, pytest, and uv.

## Setup

You need [uv](https://docs.astral.sh/uv/) and an [Anthropic API key](https://console.anthropic.com/).

1. Install the dependencies:

   ```bash
   uv sync
   ```

2. Create your environment file, then add your API key to it:

   ```bash
   cp .env.example .env
   ```

3. Create the database and fill it with fake data:

   ```bash
   uv run python -m app.db.seed
   ```

4. Start the server:

   ```bash
   uv run fastapi dev
   ```

The API runs at http://127.0.0.1:8000, with interactive docs at http://127.0.0.1:8000/docs. In the docs, click **Authorize** and enter a customer ID such as `cust_003`.

> **Help-article questions need Qdrant:** start Qdrant and store the articles as described under [Testing](#testing). Without them, Claude is told the articles can't be searched and answers without them.

> **Re-seeding deletes everything:** the seed script drops all tables, including saved conversations, and rebuilds them with the same fake data.

## Using the API

Every `/v1` endpoint needs an `Authorization: Bearer <customer_id>` header. This is deliberately simple mock authentication for a demo, so see [Known limitations](#known-limitations).

| Endpoint                             | Purpose                                                                     |
| ------------------------------------ | --------------------------------------------------------------------------- |
| `POST /v1/support/messages`          | Ask a question using the customer's data, in a new or existing conversation |
| `GET /v1/support/conversations`      | List the customer's conversations                                           |
| `GET /v1/support/conversations/{id}` | Get one conversation's questions, replies, citations and analysis           |
| `POST /v1/support/analyze`           | Classify a question without using any customer data                         |
| `GET /health`                        | Health check, with no authentication needed                                 |

### Start a conversation

```bash
curl -X POST http://127.0.0.1:8000/v1/support/messages \
  -H "Authorization: Bearer cust_003" \
  -H "Content-Type: application/json" \
  -d '{"question": "Was I charged twice in October?"}'
```

```json
{
  "reply": "No, you were not charged twice in October. October's invoice (inv_015, billing period Oct 1 to Nov 1, 2026) is for $19.00. There was one failed payment attempt on Oct 1 because of an expired card, and that attempt didn't charge you. The only successful charge was $19.00 on Oct 3, 2026, and the invoice is marked paid.",
  "citations": [],
  "analysis": {
    "category": "billing",
    "priority": "low",
    "summary": "Customer asks whether they were charged twice in October; the data shows one successful $19.00 payment for the October invoice plus one failed attempt that did not charge them, so no duplicate.",
    "suggested_response": "No, you were not charged twice in October. October's invoice (inv_015, billing period Oct 1 to Nov 1, 2026) is for $19.00. There was one failed payment attempt on Oct 1 because of an expired card, and that attempt didn't charge you. The only successful charge was $19.00 on Oct 3, 2026, and the invoice is marked paid.",
    "human_review_recommended": false
  },
  "conversation_id": "conv_bf9ba6f6ff3641bbbf26698d2fb7a8a2"
}
```

Claude's wording varies between runs, and each conversation gets its own ID.

`citations` lists the IDs of the help-article chunks that the reply's facts about Flowdesk come from, such as `refunds-and-duplicate-charges:2`, in the order Claude gave them and without repeats. It's empty when the reply uses no help articles, as above, where the answer comes from the customer's own records.

### Continue a conversation

Send the `conversation_id` from the previous response:

```bash
curl -X POST http://127.0.0.1:8000/v1/support/messages \
  -H "Authorization: Bearer cust_003" \
  -H "Content-Type: application/json" \
  -d '{"question": "What was the failure reason on that first attempt?", "conversation_id": "conv_..."}'
```

### Read conversation history

```bash
curl http://127.0.0.1:8000/v1/support/conversations \
  -H "Authorization: Bearer cust_003"
```

```bash
curl http://127.0.0.1:8000/v1/support/conversations/conv_... \
  -H "Authorization: Bearer cust_003"
```

### Classify a question

`/analyze` has no tools and sees no customer data:

```bash
curl -X POST http://127.0.0.1:8000/v1/support/analyze \
  -H "Authorization: Bearer cust_003" \
  -H "Content-Type: application/json" \
  -d '{"question": "My app keeps crashing when I open reports."}'
```

### Error responses

| Status | Meaning                                                                            | What to do                                                              |
| ------ | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `401`  | The header is missing, or the customer doesn't exist                               | Send `Bearer <customer_id>` with a seeded ID                            |
| `404`  | The conversation doesn't exist or belongs to another customer                      | Check the ID                                                            |
| `422`  | The request is invalid, such as an empty question or one over 4,000 characters     | Fix the request                                                         |
| `502`  | Claude's response was unusable, or the API rejected the request, such as a bad key | Check the server logs                                                   |
| `503`  | Claude is temporarily unavailable, or `ANTHROPIC_API_KEY` isn't set                | Follow the error message, and retry after `Retry-After` if it's present |

## How it works

### The request flow

1. Auth finds the customer from the bearer token.
2. For a follow-up, the app checks the customer owns the conversation and loads its recent turns.
3. The app calls Claude with the tools and the required output schema.
4. If Claude asks for a tool, the app runs it and sends back the result: account tools for the signed-in customer, or the help-article search with Claude's query. This repeats up to 6 calls per request.
5. The final answer is validated against a Pydantic model.
6. Only then is the turn saved.

### Design decisions

- **Customer isolation:** the account tools accept no input, so Claude has no way to ask for another customer's data. The help-article search accepts only a query and holds no customer data. Every query filters on the authenticated customer's ID. Another customer's conversation returns the same `404` as one that doesn't exist.
- **Checked citations:** every cited chunk must have been returned by a search during the same request. A made-up ID, an account record or a chunk from an earlier turn fails the reply like any other invalid output, with a `502`, so it's never shown as a source.
- **Failed turns aren't saved:** nothing is written until Claude has produced a valid answer, so a failure leaves a conversation unchanged and a retry starts cleanly.
- **Valid tool sequences:** each completed exchange is stored as one row, with its tool calls and results together, so they can't be split up.
- **History limit:** Claude sees only the 10 most recent turns (`MAX_HISTORY_TURNS` in `app/conversations.py`), which limits context growth and cost. Older turns are still stored and returned by the history endpoint.
- **Thinking blocks aren't stored:** they're sent back within a turn but dropped afterwards, because the API rejects them once earlier history changes.
- **Short database sessions:** each piece of database work opens and closes its own session, so no connection is held while waiting on Claude.
- **Time limits:** each Claude attempt is limited to 60 seconds with 2 retries, and a whole request to 150 seconds.

### Usage and logs

The server console prints each step of a request, with token usage and an estimated cost. Usage isn't stored.

```text
[Message from cust_003] Was I charged twice in October?
[LLM call 1] stop_reason=tool_use input_tokens=2232 output_tokens=79 cache_read_tokens=0 cache_write_tokens=0
  Tool use: get_invoices input={}
  Tool use: get_payments input={}
[LLM call 2] stop_reason=end_turn input_tokens=3272 output_tokens=518 cache_read_tokens=0 cache_write_tokens=0
  Text: {"reply": "...", "citations": [], "analysis": {...}}
[Request total] llm_calls=2 input_tokens=5504 output_tokens=597 cache_read_tokens=0 cache_write_tokens=0 estimated_cost=$0.000849
```

Failures are logged with their status code or stop reason, and the API request ID where there is one. The cost uses the Haiku 5.5 prices in `app/ai.py`, for prompts up to 100K tokens, so check them against [current pricing](https://www.anthropic.com/pricing) if you rely on the figure.

### Tracing

With Langfuse keys in `.env`, each `POST /v1/support/messages` request is sent to [Langfuse Cloud](https://cloud.langfuse.com) as one trace, `support-message`, with a random request ID such as `req_3f9c...`. Under it are, in order:

- **`claude-call`:** a generation for each Claude call in the tool loop, with the model the API reports and that call's input and output tokens, plus its cache-write and cache-read tokens when Anthropic sends them. Langfuse prices these with its built-in prices for the model, so each call's cost and the request's total appear in Langfuse, with no price table in the app. A call includes the SDK's own retries, so its duration includes their waits.
- **A tool observation for each tool that runs,** named after the tool, such as `get_invoices`. A `search_knowledge_base` run also has how many chunks it returned and their IDs.

Every observation has its duration, and a failed one, such as a Claude call that errors, a search that fails, or the whole request returning a `404` or `502`, is marked with the `ERROR` level, without its error message. A trace never holds the question, prompts, replies, tool inputs or results, search queries, chunk text, errors or any customer details, and the spans the Anthropic SDK makes for each Claude call aren't sent. A tool call that's rejected before it runs, such as an unknown tool, isn't recorded, and neither are requests rejected before the route runs, such as a `401` or `422`, or `/v1/support/analyze` requests.

Without the keys nothing is traced. Tracing runs alongside the request and never changes its response: if Langfuse is unreachable or fails, the error is logged and the request carries on.

## Testing

Run the test suite with:

```bash
uv run pytest
```

The tests need no API key and make no real API calls. They use temporary databases, a fake LLM service to test the routes, and a fake HTTP layer to test the real service and SDK together.

The chunking tests use the real `all-MiniLM-L6-v2` tokenizer so their token counts match the embedding model. The first run downloads it from Hugging Face, which needs internet access, and later runs use a local cache. The embedding and search tests use a fake model, so they don't download or load the real one. The storage and search tests use Qdrant's in-memory mode, so they don't need Docker and never touch your Qdrant data.

To check the demo scenarios against real Claude, run:

```bash
uv run python -m scripts.check_real_api
```

This uses your API key and costs a couple of cents. It runs on a temporary database, so `app.db` isn't touched. It also checks grounding: a policy the help articles don't cover, a feature they don't cover with a short answer that doesn't claim it's unavailable, a detail the data doesn't include, a failed search, and instructions planted in a help article. The scenarios that search need Qdrant running with the articles stored. Claude's wording varies, so it only checks for key facts, and a failure means the reply is worth reading, not necessarily that something is broken.

To chunk and embed the Markdown articles in `knowledge_base/` and store them in Qdrant, first start Qdrant with [Docker](https://www.docker.com/). Its data is kept in `qdrant_storage/`:

```bash
docker run -p 6333:6333 -p 6334:6334 -v "$(pwd)/qdrant_storage:/qdrant/storage" qdrant/qdrant
```

Then run the following. It deletes the `knowledge_base` collection and rebuilds it with the chunks and their embeddings, using cosine distance, and records the embedding model in the collection's metadata. It doesn't need the FastAPI server or an API key. The first run downloads the `all-MiniLM-L6-v2` model from Hugging Face, and later runs use a local cache:

```bash
uv run python -m scripts.ingest
```

You can browse the stored chunks in Qdrant's dashboard at http://localhost:6333/dashboard.

To see what a search finds, pass one or more queries in quotes. Each result shows its cosine similarity score, chunk ID, section heading and a preview of its text. Add `--limit 3` to change how many results each query shows, or `--full` to print each chunk's whole text. Loading the model takes a few seconds, so passing several queries in one run is quicker than running it once per query:

```bash
uv run python -m scripts.search "I was charged twice" "How do I cancel my subscription?"
```

To search only one article, add `--document-id` with the article's file name in `knowledge_base/`, without `.md`. An ID that matches no article gives no results:

```bash
uv run python -m scripts.search "I was charged twice" --document-id cancellation
```

To measure how well search finds the right articles, run the following. It searches for each of the 20 labeled questions in `eval/retrieval_cases.json`, ranks articles by their best-matching chunk, and judges each question on its first 5 different articles. It reports Hit@1, Hit@3, Hit@5 and Mean Reciprocal Rank overall, by category and per question, then lists any question with no relevant article in its top 5. A question with several relevant articles counts as a hit if any of them appears. It doesn't use FastAPI or Claude:

```bash
uv run python -m scripts.evaluate_retrieval
```

There are only 8 articles, so any 5 of them cover most of the knowledge base, and even a random order would reach about 0.77 Hit@5 on this dataset. Hit@1 and MRR say more about search quality.

The same run then evaluates chunks for every question, using its `answer_chunk_ids`. It takes the top 5 chunks exactly as search returns them, so several chunks can come from one article. Only chunks labeled as answering the question count as relevant. Chunks in `mention_chunk_ids` only mention the topic or link to the answer, so they count as irrelevant, but the report marks them. It reports Hit@1, Hit@3, Hit@5, Precision@3, Precision@5 and MRR. It then lists questions where an irrelevant chunk ranks above an answer, questions with no answer chunk in the top 5, and which answer chunks were found for multi-document questions. Precision divides by the number of places, so a question with one answer chunk can't score above 0.20 for Precision@5. The report shows the best possible scores for comparison.

Chunks are labeled from their text alone, never from search results, using these rules:

- **Answer:** on its own, the chunk addresses the customer's situation and resolves it. For an ambiguous question, that can be one interpretation of it, and for a two-part question, one part. For a "how do I" question, the chunk must give the action, and for a "will", "do" or "does" question, the outcome. A fact written for a different situation, such as an example about expired cards, doesn't count.
- **Mention:** the chunk names the question's situation or task, or links to the section that answers it, but doesn't resolve it. This includes related facts written for a different situation.
- **Neither:** chunks that only share words with the question.

Each answer chunk has a quote from its text in `answer_evidence`. The labels name chunk IDs from `scripts/ingest.py`, so they're checked before every run, and by a test:

- Every labeled chunk exists, and none is both an answer and a mention.
- Every quote is in its chunk. Any other chunk that contains it, such as the overlapping start of the next chunk, must also be labeled as an answer.
- A question's answer chunks come from exactly its `relevant_document_ids`.

The run also checks that Qdrant holds exactly the chunks the ingest script would make from the current articles, embedded with the current model. If the articles or chunking changed and the labels or Qdrant data weren't updated, it stops and lists the problems instead of scoring against stale text.

`eval/baseline_report.txt` is the full report from before any retrieval improvements. The report is the same on every run with the same articles, model and Qdrant data, so to see exactly which scores and questions a change moved, compare a new run against it:

```bash
uv run python -m scripts.evaluate_retrieval | diff eval/baseline_report.txt -
```

With 20 questions, one question moves Hit@1 by 0.05, so check which questions changed rather than relying only on the averages.

To review the whole assistant end to end, run the following. It sends each of the 12 questions in `eval/assistant_cases.json` through the real `/v1/support/messages` route as a seeded customer, with real Claude calls, tools and help-article search. That covers 3 help-article questions, 2 account questions, 2 that need both, 3 where the evidence is missing or the question is ambiguous, and 2 multi-part questions. It uses your API key and costs a few cents, so it only runs when you start it. Like the real-API check, it uses a temporary seeded database and leaves `app.db` alone. Qdrant must be running with the articles stored:

```bash
uv run python -m scripts.evaluate_assistant > assistant_report.md
```

The Markdown report lists each case's question and expected behavior next to what happened: the tools used, compared with those expected; each search's query and returned chunks; the reply; the text of each cited chunk; the analysis; and the time taken. Nothing is scored, because whether an answer is right, grounded and well cited needs a person to judge, so each case ends with a checklist to fill in. Progress goes to the terminal. To rerun only some cases, add `--case` with a case ID, once per case:

```bash
uv run python -m scripts.evaluate_assistant --case kb-invoice-pdf --case multi-upgrade-annual > assistant_report.md
```

To also have Claude judge whether each reply is faithful to the tool results behind it, add `--judge`. For each answered case, the judge model set in `scripts/judge_faithfulness.py` (`claude-sonnet-5-5`) reads the question, the reply and every tool result the assistant got, both help-article passages and the customer's records. It labels each factual claim in the reply as supported, unsupported, contradicted, or uncertain when the reply says it couldn't confirm something. A reply passes when no claim is unsupported or contradicted, and the report lists the claims that failed with the judge's reasons. The judge never sees the expected behavior or the golden dataset, so it checks faithfulness, not whether the answer is right. It's one more Claude call per case on a pricier model, so it only runs when you ask. A failed or malformed judgment shows as an error for that case without stopping the run. Evaluation runs are never traced in Langfuse, with or without the judge:

```bash
uv run python -m scripts.evaluate_assistant --judge > assistant_report.md
```

`eval/golden_dataset.json` holds the reference answer for each of the 12 cases, grounded in the seeded records and help articles. It repeats each case unchanged and adds the facts a complete answer must give, optional facts worth crediting, claims that make an answer wrong, and what the data can't establish. Facts are judged on meaning, not wording. `scripts/validate_golden_dataset.py` explains each field. To check the file after editing it, run the following. It makes no API calls:

```bash
uv run python -m scripts.validate_golden_dataset
```

To also check each reply against the golden dataset, add `--correctness`. The same judge model gets the question, the reply and the case's golden expectations, never the tool results. It checks, on meaning rather than wording, whether the reply gets each required fact across, makes any prohibited claim, or claims an answer to something the data can't establish, and lists any other claim that contradicts the golden facts. A reply passes when it has every required fact and breaks no expectation. Optional facts never count against it, and where a case accepts a clarifying question, asking one stands in for the required facts. Correctness has its own verdict, column and section in the report, apart from faithfulness, and costs one more Claude call per case, so it only runs when you ask. Use both flags for both checks:

```bash
uv run python -m scripts.evaluate_assistant --judge --correctness > assistant_report.md
```

## Known limitations

This is a local demo, and these are deliberate or accepted gaps:

- **Authentication is a mock:** customer IDs are guessable and act as credentials, so anyone with an ID can read that customer's data. A real service needs proper authentication.
- **No rate limiting or spend cap:** any valid customer ID can spend API credit.
- **No migrations:** startup adds missing tables, but changing an existing table means re-seeding, which deletes conversations.
- **Single-message concurrency only:** two messages sent at once in a conversation won't see each other, and resending a message stores it twice.
- **Stale data in history:** old tool results stay in the conversation. The prompt tells Claude to look current data up again, which is an instruction and not a guarantee.
- **Analysis is visible to customers:** `analysis` is returned with every reply, so a real client should decide what to show.
- **Customer data in plain text:** questions and tool results are stored unencrypted, and the console prints customers' questions and replies.
- **Closed accounts aren't blocked:** `account_status` isn't enforced.
- **Claude doesn't know today's date:** it can state a due date, but not reliably say how far away it is.
- **Plan details are placeholders:** the Starter and Business prices, descriptions and features are made up.
- **Search holds up the server:** it runs synchronously, and the first search after starting loads the embedding model, which takes a few seconds. Other requests wait meanwhile, and the request time limit can't interrupt it.
- **Re-ingesting empties the knowledge base first:** the collection is deleted and rebuilt, so searches during a run find nothing, and a run that fails partway through storing leaves it empty until the next successful run.
